## 1. How to run a review

| Step | Name | Do |
| --- | --- | --- |
| 1 | Scope and profile | Record target, version or commit, profile and applicability flags. Declare the questions the review must answer. |
| 2 | Inventory | Dissect the repository (dissect scan) and collect automated evidence (rqs probe). |
| 3 | Claims | List headline claims and mark each as measured, unmeasured or contradicted. |
| 4 | Oracle | For tools, build an independent answer key for at least five questions and run the product against it. Otherwise record U. |
| 5 | Score | Score each applicable criterion with level, confidence and evidence. Use U when the evidence is not there. |
| 6 | Gap sweep | Apply lenses G1-G14. No case, no finding. |
| 7 | Opportunity sweep | Apply lenses O1-O14 and score OPP-1..7 with priority. |
| 8 | Re-engineering | Choose actions from the matrix with expected gains and how they will be measured. |
| 9 | Integrity | A second reviewer independently scores at least 20 percent of the criteria. Report agreement and adjudicate differences. Disclose conflicts of interest; own projects get an adversarial reviewer. |
| 10 | Report | Publish the JSON scorecard and the Markdown report with date, standard version and commit. Re-review on every major release or yearly. |

Quick start with the tooling: `tools/rqs/rqs.sh probe <repo> > evidence.json`, score the criteria in a review file (`rqs.sh template` prints one), then `rqs.sh score evidence.json review.json` and `rqs.sh report scorecard.json`.

## 2. Principles

- **evidence.** No case, no finding. Every score cites evidence (a file, a command and its output, a measurement); opinions are labelled as inferences.
- **unknown.** Unknown is neither pass nor fail. Unevidenced criteria score U, lower evidence coverage, and can cap a grade. They never count as a pass.
- **oracle.** Prefer independent oracles (answer keys, golden outputs, reference implementations) over a project's description of itself.
- **profile.** Judge against the product's profile (what it is for), not against an ideal product.
- **horizon.** Level 3 is good practice today (2025-26 standards). Level 5 is what users, agents and regulators will expect in 2030-35. Both are stated explicitly for every criterion.
- **agents-are-users.** AI agents are first-class users. Interfaces, errors, costs and guarantees must work for a non-human caller with a finite context window.
- **honest-numbers.** Report measured numbers with method and date, including net-negative cases. Never round toward the desired conclusion.
- **proportionality.** Effort, risk and rigour scale with impact. A 10-file skill and a code-executing agent harness are not held to the same weights.
- **opportunity.** A review is incomplete until it has also looked for what could be extracted, merged, deleted, re-platformed or standardized.

## 3. Scale: levels and confidence

| Level | Name | Meaning |
| --- | --- | --- |
| 0 | Absent or harmful | The capability is missing, or is present in a way that creates risk or misleads. |
| 1 | Ad hoc | Something exists but is informal, undocumented or untested. |
| 2 | Partial | Implemented or documented for some paths. Known gaps remain. |
| 3 | Meets | Meets the 'meets' anchor, which is current good practice. |
| 4 | Enforced and measured | Meets, and is enforced by automation (CI gates, metrics, regression checks). |
| 5 | Horizon-ready | Meets the 'horizon' anchor, which is what 2030-35 users, agents and regulators will expect. |
| U | Unknown | Not enough evidence to score. Counts against evidence coverage; never a pass. |
| NA | Not applicable | Excluded with a stated reason (for example, no UI or no cryptography). |

| Confidence | Weight | Meaning |
| --- | --- | --- |
| observed | 1.0 | Read directly from the repository, a run, or tool output. |
| derived | 0.9 | Computed from observed evidence by a stated rule. |
| inferred | 0.6 | Reviewer judgement from indirect signals. |

## 5. Applicability flags

Criteria with `applies if` are scored only when the flag is set; otherwise they are NA.

- `uses_llm`: The product calls LLMs, runs agents, or is executed by agents (MCP server, skill, harness).
- `has_ui`: The product has a graphical, web or terminal UI for people.
- `executes_code`: The product runs code, commands or browsers on behalf of a user or agent.
- `parses_untrusted`: The product parses input it does not control (binaries, archives, web content, repositories, model files).
- `uses_crypto`: The product signs, encrypts, authenticates or verifies with cryptography.
- `heavy_compute`: Training, inference, large builds or analyses with material energy use.
- `network_service`: The product listens on a network port or exposes an API.
- `distributed`: The product is published for others to install (package registry, binaries, app store).

## 6. Criteria

Each criterion states the question, why it matters, and anchors for a failing score (0-1), today's good practice (3) and the 2030-35 horizon (5). **Core** criteria weigh double; **red line** criteria cap the grade (section 8).

### PUR: Purpose and value

*The product knows whom it serves, proves its value with measurements, and carries no surface it does not need.* ISO/IEC 25010: functional suitability.

#### PUR-1 Problem, users and limits are explicit

**Question.** Can a new human or agent user tell in under two minutes what this is for, who it is for, and where it stops?

**Why.** Agents choose tools from descriptions. Vague scope causes misuse, and misuse is the main source of wrong agent output.

- **Fails (0-1):** No README, or marketing language with no stated scope, non-goals or limitations.
- **Meets (3):** README states the problem, the intended users (including agents), how to start, and its known limitations and non-goals.
- **Horizon (5):** A machine-readable capability statement (inputs, outputs, effects, limits, costs) is published next to the prose and kept in sync by CI.
- **Evidence:** README, docs index, describe/--help output. **Probes:** `meta.readme_sections`, `agent.describe`. **Refs:** ISO25010.

#### PUR-2 Value claims are measured and reproducible (core)

**Question.** Is every headline number backed by a harness someone else can rerun, with baseline, sample size, uncertainty and date?

**Why.** In 2030 buyers, agents and auditors will discount unmeasured claims. Reproducible evaluation is the currency of trust.

- **Fails (0-1):** Headline numbers without method, baseline or harness, or numbers contradicted by a rerun.
- **Meets (3):** Benchmarks are in the repo with method, baseline, sample size and date. Net-negative cases are reported.
- **Horizon (5):** Benchmarks run in CI with confidence intervals; results are versioned per release and independently reproduced.
- **Evidence:** benchmark harness, results files, claim-to-harness mapping. **Probes:** `claims.count`, `claims.harness`, `test.bench`. **Refs:** ISO25010.

#### PUR-3 Necessity and scope discipline

**Question.** Does each component, dependency and tool earn its place, or does an existing one already do it?

**Why.** Every unneeded tool, dependency and line costs agent context, attack surface and maintenance for the life of the product.

- **Fails (0-1):** Large surfaces with no measured use; reimplementations of standard-library or dependency features; duplicated subsystems.
- **Meets (3):** There is a documented reason for each major component. Duplicates and reimplementations are justified or removed.
- **Horizon (5):** A necessity gate (does it exist already? can stdlib or a dependency do it?) runs before additions, and surface size is tracked per release.
- **Evidence:** dependency list, tool/command counts, duplication report, dead-code report. **Probes:** `size.duplicates`, `deps.counts`, `agent.mcp`, `static.deadcode_tools`. **Refs:** ISO5055.

### COR: Correctness and verification

*The product does what it says, and proves it against oracles that are independent of the product.* ISO/IEC 25010: functional suitability, reliability.

#### COR-1 Automated tests cover behaviour and gate changes (core)

**Question.** Do tests exercise the behaviour users depend on, and does CI block merges that break them?

**Why.** Agent-written code will be the bulk of new code by 2030. Tests are the contract that keeps fast change safe.

- **Fails (0-1):** No tests, or tests that are not run in CI.
- **Meets (3):** Unit and integration tests cover the main paths and run on every change. The test-to-source ratio is reported.
- **Horizon (5):** Coverage of critical paths is measured and enforced; flaky tests are tracked and quarantined with owners; tests run on every supported platform.
- **Evidence:** test files, CI workflow, coverage config. **Probes:** `test.ratio`, `test.frameworks`, `ci.tests_in_ci`, `ci.os_matrix`. **Refs:** ISO25010, NIST-SSDF.

#### COR-2 Independent oracles

**Question.** Is output checked against something the product did not produce itself (answer keys, golden files, reference implementations, differential tests)?

**Why.** Self-consistent but wrong output passes ordinary tests. Oracles catch what the product cannot see about itself.

- **Fails (0-1):** Only self-referential tests (snapshots of current output with no external truth).
- **Meets (3):** Golden outputs or answer keys derived independently exist for the main capabilities.
- **Horizon (5):** Differential tests against reference tools or prior versions run in CI. Parity tolerances are explicit. Oracles are refreshed when inputs change.
- **Evidence:** fixtures with provenance, parity tests, answer keys. **Probes:** `test.golden`, `test.e2e`. **Refs:** ISO25010.

#### COR-3 Test strength is measured

**Question.** Are the tests themselves tested (mutation testing, property-based tests, fuzzing for untrusted-input parsers)?

**Why.** High coverage with weak assertions is false comfort. Parsers of untrusted input need fuzzing to be trustworthy.

- **Fails (0-1):** No mutation, property or fuzz testing anywhere.
- **Meets (3):** Property tests or fuzzers cover parsers and core algorithms; mutation testing runs at least periodically.
- **Horizon (5):** Mutation score and fuzz coverage are tracked per release with thresholds; crashes found by fuzzing become regression tests.
- **Evidence:** mutation config and reports, property tests, fuzz targets. **Probes:** `test.mutation`, `test.property`, `test.fuzz`. **Refs:** ISO5055, OPENSSF.

#### COR-4 Self-application and dogfooding

**Question.** Has the product been run on itself, its own artifacts, or realistic third-party inputs, with the results recorded?

**Why.** A tool that cannot handle its own shipped form usually fails on real users' inputs too (REA could not inventory its own npm package).

- **Fails (0-1):** Only synthetic toy inputs.
- **Meets (3):** Realistic inputs are used in tests or documented trials, including the product's own artifacts where meaningful.
- **Horizon (5):** Self-application runs in CI on every release, and its findings are tracked to closure.
- **Evidence:** real-input test lanes, self-analysis reports. **Probes:** `test.e2e`, `ci.workflows`. **Refs:** ISO25010.

#### COR-5 Determinism and reproducibility of results

**Question.** Does the same input give the same output and identifiers, and are sources of nondeterminism controlled?

**Why.** Agents cache, compare and share results. Nondeterminism breaks caching, diffing and audit.

- **Fails (0-1):** Output varies between identical runs without explanation, for example timing treated as behaviour.
- **Meets (3):** Core outputs are deterministic, or nondeterminism is documented and isolated (seeds, timestamps, ordering).
- **Horizon (5):** Outputs carry content-addressed identifiers. Reproducibility is tested by running twice and comparing in CI.
- **Evidence:** double-run comparisons, id scheme. **Probes:** `epi.evidence`. **Refs:** ISO25010.

### REL: Reliability, durability and resource safety

*Work survives crashes and large inputs. Failures are bounded, labelled and recoverable.* ISO/IEC 25010: reliability.

#### REL-1 Crash safety and resumability (core)

**Question.** If the process is killed mid-task, is completed work kept and resumed without repeating side effects?

**Why.** Agents run long, multi-step tasks. Losing state on a crash wastes compute and can repeat side effects such as payments, writes or messages.

- **Fails (0-1):** State lives only in memory; a crash loses everything; retries repeat side effects.
- **Meets (3):** Long tasks checkpoint to durable storage; replays are idempotent; a kill-and-resume test exists.
- **Horizon (5):** Durable execution with idempotency keys and leases; crash-loop protection; resume is verified by automated fault injection.
- **Evidence:** kill/resume test, checkpoint storage, idempotency keys. **Probes:** `dur.checkpoint`, `dur.storage`, `dur.retry`. **Refs:** ISO25010.

#### REL-2 Bounded resources and no size cliffs

**Question.** Are memory, time and output size bounded and documented, and do large inputs degrade gracefully instead of failing?

**Why.** Inputs grow faster than machines. Single-object limits (strings, frames, buffers) become outages (REA could not re-import its own 889 MB export).

- **Fails (0-1):** Unbounded memory or output; failures on large inputs with no limit stated.
- **Meets (3):** Limits exist for memory, time and output, and are documented; large results stream or page.
- **Horizon (5):** Streaming everywhere for unbounded data; limits are configurable and tested at 10x the expected maximum; resource use is reported per operation.
- **Evidence:** limit configs, streaming paths, large-input tests. **Probes:** `risk.patterns`, `agent.budget`. **Refs:** ISO5055, OWASP-LLM.

#### REL-3 Graceful degradation and honest partial results

**Question.** When something fails or is skipped, is the result labelled partial, and do retries back off instead of crash-looping?

**Why.** Silent partial results are worse than errors; they become false facts downstream.

- **Fails (0-1):** Failures swallowed; partial output presented as complete.
- **Meets (3):** Partial results are labelled with what is missing. Retries use backoff with limits.
- **Horizon (5):** Each failure mode is enumerated, tested and documented, with fail-closed defaults where safety matters.
- **Evidence:** error handling, partial-result labels, retry policy. **Probes:** `dur.retry`, `agent.structured_errors`. **Refs:** ISO25010.

#### REL-4 Lifecycle hygiene

**Question.** Are child processes, temporary files, locks, ports and sessions always cleaned up, including after errors and signals?

**Why.** Leaked processes and files accumulate on agent hosts and become security and stability problems.

- **Fails (0-1):** Orphans or leftovers are common, and no signal handling exists.
- **Meets (3):** Cleanup on success, error and SIGINT/SIGTERM; owned processes are tracked.
- **Horizon (5):** Cleanup is verified by tests that check for leftovers; ownership is proven (process groups, job objects, run tokens).
- **Evidence:** signal handlers, cleanup tests. **Probes:** `obs.signals`. **Refs:** ISO25010.

### PERF: Efficiency and sustainability

*Time, attention (tokens) and energy are spent deliberately and measured.* ISO/IEC 25010: performance efficiency.

#### PERF-1 Latency and throughput are measured

**Question.** Are the main operations timed (p50/p99) with documented budgets?

**Why.** An agent workflow is a chain of calls; slow steps multiply.

- **Fails (0-1):** No performance numbers; obvious hot-path waste.
- **Meets (3):** Benchmarks for the main operations, with budgets.
- **Horizon (5):** Performance regressions are gated in CI; budgets are declared to callers (expected latency per operation).
- **Evidence:** benchmarks, CI perf jobs. **Probes:** `test.bench`. **Refs:** ISO25010.

#### PERF-2 Attention economy (tokens and bytes an agent must read) (core)

**Question.** How many bytes or tokens does an agent pay per useful answer, including tool catalogs and repeated payloads?

**Why.** Context is the agent's scarcest resource. Catalogs and verbose outputs are paid for on every turn (REA's default catalog is about 833k tokens).

- **Fails (0-1):** Megabyte catalogs or outputs by default; duplicated payloads; no summaries.
- **Meets (3):** Outputs are summary-first with detail on request; catalog size is measured and reasonable for the scope.
- **Horizon (5):** Every output states its cost; schemas are lazy or compact by default; one payload copy; detail is retrieved by stable handle.
- **Evidence:** tools/list size, output size per operation. **Probes:** `agent.mcp`, `agent.json_output`. **Refs:** MCP, OWASP-LLM.

#### PERF-3 Energy and carbon awareness (applies if `heavy_compute`)

**Question.** For compute-heavy work, is energy or carbon measured, and are efficient paths (on-device, smaller models, caching) offered?

**Why.** AI workloads drive energy demand, and carbon reporting is spreading through procurement and regulation.

- **Fails (0-1):** Heavy compute with no measurement and no efficient option.
- **Meets (3):** Energy or time per unit of work is measured for heavy paths; caching or reuse avoids repeated compute.
- **Horizon (5):** SCI (ISO/IEC 21031) or equivalent is reported per functional unit; the product can choose low-energy paths automatically.
- **Evidence:** energy benchmarks, caching. **Probes:** `test.bench`, `perf.energy`. **Refs:** ISO21031.

### SEC: Security and supply chain

*Built, shipped and run securely, with verifiable provenance and a path to post-quantum cryptography.* ISO/IEC 25010: security.

#### SEC-1 Security policy and threat model (core)

**Question.** Is there a way to report vulnerabilities, and a written threat model for what the product protects and does not?

**Why.** The EU CRA requires coordinated vulnerability handling for products with digital elements; agents need to know trust boundaries.

- **Fails (0-1):** No SECURITY.md or contact; no statement of what is trusted.
- **Meets (3):** SECURITY.md with contact and response expectations; a threat model or trust-boundary section.
- **Horizon (5):** Security advisories are published (GHSA/CVE/CSAF); the threat model is reviewed each release; disclosure timelines are met and measured.
- **Evidence:** SECURITY.md, threat model doc, advisories. **Probes:** `meta.security_policy`. **Refs:** NIST-SSDF, EU-CRA, OPENSSF.

#### SEC-2 Dependency hygiene

**Question.** Are dependencies locked, minimal, updated and scanned for known vulnerabilities?

**Why.** Most compromises arrive through dependencies (OWASP LLM03 supply chain).

- **Fails (0-1):** No lockfiles; unpinned ranges for runtime dependencies; no update or scan process.
- **Meets (3):** Lockfiles committed; automated update PRs; known-vulnerability scanning in CI.
- **Horizon (5):** Dependencies minimal and justified; install scripts disabled or audited; new dependencies reviewed by policy.
- **Evidence:** lockfiles, dependabot/renovate config, scan jobs. **Probes:** `deps.lockfiles`, `deps.update_bot`, `deps.pinning`, `ci.security_scans`. **Refs:** OPENSSF, OWASP-LLM, NIST-SSDF.

#### SEC-3 Build provenance and signed releases (applies if `distributed`)

**Question.** Can a user verify who built a release, from which source and how?

**Why.** Provenance attestations are becoming standard expectations for distributed software.

- **Fails (0-1):** Releases built on developer machines; nothing signed.
- **Meets (3):** Releases built in CI with provenance (npm provenance, PyPI attestations, Sigstore, or the SLSA generator).
- **Horizon (5):** SLSA Build L3, reproducible builds, verification instructions for users, and signatures planned for post-quantum algorithms.
- **Evidence:** release workflow, attestations. **Probes:** `ci.provenance`, `ci.release_automation`. **Refs:** SLSA, SIGSTORE, CNSA2.

#### SEC-4 SBOM and VEX (applies if `distributed`)

**Question.** Does each release ship a machine-readable SBOM, and are known vulnerabilities triaged (VEX)?

**Why.** SBOMs are required for products with digital elements under the EU CRA from Dec 2027, and buyers already request them.

- **Fails (0-1):** No SBOM; no record of third-party components.
- **Meets (3):** SBOM (SPDX or CycloneDX) generated per release; third-party notices complete.
- **Horizon (5):** SBOM and AI-BOM (models, datasets) per release, VEX statements for known CVEs, and SBOMs signed together with the release.
- **Evidence:** SBOM files, notices. **Probes:** `ci.sbom`, `meta.notices`. **Refs:** SBOM, EU-CRA.

#### SEC-5 CI and automation hardening

**Question.** Are workflows least-privilege, actions pinned by digest, and untrusted triggers handled safely?

**Why.** CI is a supply-chain entry point. Unpinned actions and broad tokens have caused real compromises.

- **Fails (0-1):** Actions pinned by tag only; write-all tokens; pull_request_target running untrusted code.
- **Meets (3):** Actions pinned by full SHA; explicit minimal permissions; untrusted triggers isolated.
- **Horizon (5):** OpenSSF Scorecard (or equivalent) gating; signed commits or tags for releases; workflow changes require review.
- **Evidence:** workflow files. **Probes:** `ci.pinned_actions`, `ci.permissions`, `ci.pull_request_target`. **Refs:** OPENSSF, SLSA.

#### SEC-6 Secrets and sensitive data (red line)

**Question.** Are there no secrets in the repository, and are secrets kept out of logs, outputs and telemetry?

**Why.** Leaked credentials are the most common cause of breaches; agents amplify leaks by copying outputs.

- **Fails (0-1):** Live secrets committed, or secrets printed in logs or outputs.
- **Meets (3):** No secrets in the repository; a secret scanner runs; secrets are redacted in logs and outputs.
- **Horizon (5):** Short-lived, scoped credentials (OIDC, workload identity); secret redaction is tested; agent-visible outputs are scrubbed by design.
- **Evidence:** secret scan results, redaction code. **Probes:** `risk.secrets`, `ci.security_scans`. **Refs:** OWASP-ASVS, OWASP-LLM.

#### SEC-7 Dangerous operations (red line)

**Question.** Is the code free of injection-prone patterns (shell strings, eval, unsafe deserialization, disabled TLS verification, path traversal)?

**Why.** These patterns turn untrusted input, including prompt-injected agent input, into code execution.

- **Fails (0-1):** Injection-prone patterns on paths reachable from untrusted input.
- **Meets (3):** No such patterns in production code, or each one is justified and constrained.
- **Horizon (5):** Static analysis gates these classes in CI; untrusted inputs are typed and validated at every boundary.
- **Evidence:** pattern scan, SAST results. **Probes:** `risk.patterns`, `risk.tls_off`, `risk.unsafe_deser`. **Refs:** OWASP-ASVS, ISO5055, CISA-SBD.

#### SEC-8 Safe parsing of untrusted input (applies if `parses_untrusted`)

**Question.** Are parsers of untrusted data memory-safe or sandboxed, size-limited and fuzzed?

**Why.** Parsing attacker-controlled bytes is the classic exploit path. CISA asks vendors to publish memory-safety roadmaps.

- **Fails (0-1):** Native-code parsers of untrusted input with no limits or fuzzing.
- **Meets (3):** Memory-safe language or sandboxed parser process; size and recursion limits; malformed-input tests.
- **Horizon (5):** Parsers are fuzzed continuously, run with least privilege in isolation, and the memory-safety roadmap is published.
- **Evidence:** parser code, limits, fuzz targets. **Probes:** `test.fuzz`, `agent.sandbox`. **Refs:** CISA-SBD, ISO5055.

#### SEC-9 Crypto-agility and post-quantum readiness (applies if `uses_crypto`)

**Question.** Is cryptography used through a replaceable layer with an inventory of algorithms, and is there a plan for ML-KEM/ML-DSA?

**Why.** NIST's draft transition deprecates quantum-vulnerable public-key algorithms after 2030 and disallows them after 2035; CNSA 2.0 requires post-quantum signing for software by 2030.

- **Fails (0-1):** Hard-coded classical algorithms scattered through the code, no inventory.
- **Meets (3):** The algorithm inventory is documented; cryptography sits behind an abstraction; no deprecated algorithms are used for security.
- **Horizon (5):** Hybrid or post-quantum algorithms (ML-KEM, ML-DSA, SLH-DSA) supported for key exchange and signatures, with a dated migration plan.
- **Evidence:** crypto usage inventory, abstraction layer. **Probes:** `crypto.classical`, `crypto.pqc`. **Refs:** NIST-PQC, CNSA2.

### AGT: AI and agent safety

*Where LLMs or agents are involved, the product resists manipulation, limits agency, isolates execution and keeps people in control.* ISO/IEC 25010: safety, security.

#### AGT-1 Prompt-injection resilience (core, applies if `uses_llm`)

**Question.** Is untrusted content (web pages, files, repositories, tool output) marked and separated from instructions, and tested against injection?

**Why.** Prompt injection is OWASP LLM01; agents read untrusted content constantly.

- **Fails (0-1):** Untrusted content flows into prompts or tool arguments unmarked and untested.
- **Meets (3):** Untrusted content is labelled (for example untrusted_content flags); instruction and data channels are separated; injection cases are tested.
- **Horizon (5):** An adversarial corpus runs in CI per model version; actions caused by injected content are blocked by policy, not by prompt wording.
- **Evidence:** untrusted markers, injection tests. **Probes:** `agent.prompt_injection`. **Refs:** OWASP-LLM, OWASP-AGENTIC, MITRE-ATLAS.

#### AGT-2 Least agency and honest effect declarations (applies if `uses_llm`)

**Question.** Do tools and actions have the minimum permissions they need, do destructive actions require approval or dry-run, and are effect hints accurate?

**Why.** Excessive agency is OWASP LLM06. Hosts auto-approve on declared hints, so wrong hints are either unsafe or useless.

- **Fails (0-1):** Broad default permissions; destructive actions without confirmation; hints that are wrong.
- **Meets (3):** Scoped permissions, approval or dry-run for destructive actions, accurate readOnly/destructive/idempotent hints.
- **Horizon (5):** Capabilities are declared as machine-checkable policy; permissions are granted per task and expire.
- **Evidence:** permission model, annotations, dry-run modes. **Probes:** `agent.approval`, `agent.mcp`. **Refs:** OWASP-LLM, MCP, OWASP-AGENTIC.

#### AGT-3 Human oversight and reversibility (applies if `uses_llm`)

**Question.** Can a person see, approve, pause and undo what the product or its agents do?

**Why.** Oversight is a core expectation of the EU AI Act and of every AI risk framework; it is also what makes people willing to delegate.

- **Fails (0-1):** Consequential actions happen without a record, and cannot be stopped or undone.
- **Meets (3):** A readable action log exists, consequential actions need approval, and the product has a stop control and documented rollback.
- **Horizon (5):** Oversight is designed per risk level with tested rollback, and the audit trail can be exported in an open format.
- **Evidence:** action log, approval flow, rollback docs. **Probes:** `agent.approval`. **Refs:** EU-AIA, ISO42001, NIST-AIRMF, ISO25059.

#### AGT-4 Evaluation of model-dependent behaviour (core, applies if `uses_llm`)

**Question.** Is there an evaluation suite for the behaviour that depends on models or prompts, run when models, prompts or providers change?

**Why.** Model updates silently change behaviour. Without regression evaluation, quality drifts unnoticed.

- **Fails (0-1):** No evaluation; prompt or model changes are shipped on intuition.
- **Meets (3):** An evaluation set with expected outcomes exists and is run before releases; results are recorded.
- **Horizon (5):** Evaluations run in CI per model and provider version with confidence intervals; regressions block release; results are published.
- **Evidence:** eval harness, results history. **Probes:** `test.bench`, `claims.harness`. **Refs:** NIST-AIRMF, ISO25059.

#### AGT-5 AI transparency and disclosure (applies if `uses_llm`)

**Question.** Are models, datasets, providers and data flows documented, and is AI-generated output disclosed where it matters?

**Why.** Transparency duties in the EU AI Act, procurement rules and user trust all depend on knowing what model did what with which data.

- **Fails (0-1):** Unknown providers or models; user data sent to third parties without disclosure.
- **Meets (3):** The providers, models and data flows in use are documented; model or data cards for any shipped models; AI-generated artefacts are marked.
- **Horizon (5):** AI-BOM (models, datasets, prompts) per release, and content credentials for generated media where relevant.
- **Evidence:** model cards, provider docs, AI-BOM. **Probes:** `agent.llm_usage`, `ci.sbom`. **Refs:** EU-AIA, SBOM, C2PA, ISO42001.

#### AGT-6 Consumption limits and cost visibility (applies if `uses_llm`)

**Question.** Are tokens, time, money and calls bounded per task, and reported to the user?

**Why.** Unbounded consumption is OWASP LLM10. Agents in loops can spend without limit.

- **Fails (0-1):** No budgets or limits; costs are invisible.
- **Meets (3):** Per-task limits on tokens, time and calls; cost or usage is reported after each run.
- **Horizon (5):** Budgets are declared before work starts and enforced, and cost is attributed per step and per outcome.
- **Evidence:** budget settings, usage reports. **Probes:** `agent.budget`. **Refs:** OWASP-LLM.

### INT: Interfaces and interoperability

*Humans and agents can use the product through open, versioned, self-describing interfaces with actionable errors.* ISO/IEC 25010: compatibility, interaction capability.

#### INT-1 Open, versioned interfaces (core)

**Question.** Is the product usable through open protocols or documented APIs (MCP, a CLI with JSON, HTTP/OpenAPI, A2A), with version negotiation and a compatibility policy?

**Why.** Agents compose tools across vendors. Proprietary or unversioned interfaces break every client when they change.

- **Fails (0-1):** Only an undocumented or GUI-only interface.
- **Meets (3):** A documented CLI with JSON output and/or a standard protocol (MCP, OpenAPI); interface versions are stated.
- **Horizon (5):** Several standard protocols are supported; capabilities are negotiated; old clients keep working for a declared window.
- **Evidence:** protocol implementation, API docs, version policy. **Probes:** `agent.mcp`, `agent.a2a`, `agent.openapi`, `agent.json_output`. **Refs:** MCP, A2A.

#### INT-2 Machine-readable contract and self-description

**Question.** Can an agent discover the commands, inputs, outputs, effects and limits from the product itself?

**Why.** Agents should not need to read prose to call a tool correctly; contracts in data prevent misuse.

- **Fails (0-1):** Behaviour discoverable only from prose or source.
- **Meets (3):** Schemas for inputs and outputs, a describe or --help --json command, and stable field names.
- **Horizon (5):** The contract is versioned, diffable and published with each release, and drift between the contract and the code fails CI.
- **Evidence:** schemas, describe output. **Probes:** `agent.describe`, `agent.json_output`. **Refs:** MCP.

#### INT-3 Small, composable surface

**Question.** Is the number of tools, commands and options proportionate, with composable primitives rather than one tool per case?

**Why.** Every tool definition is paid for in context, and large menus degrade tool selection.

- **Fails (0-1):** Hundreds of narrowly different tools or commands with overlapping effects.
- **Meets (3):** Surface size is measured and justified; related operations share one parameterised tool.
- **Horizon (5):** Core tools are a small set (tens, not hundreds) with optional lazy-loaded extensions, and tool-selection accuracy is measured.
- **Evidence:** tool/command counts, catalog bytes. **Probes:** `agent.mcp`. **Refs:** MCP.

#### INT-4 Actionable, consistent errors

**Question.** Do errors carry a stable code, the real cause, a fix, and a correct retryable flag, and does the same mistake always give the same code?

**Why.** An agent can only repair a call it understands. Misleading errors cause loops (REA reported a missing qualification as 'state changed, retry').

- **Fails (0-1):** Free-text errors, swallowed causes, or misleading retry advice.
- **Meets (3):** Typed error codes with cause and remediation; retryable flags are correct; the error schema is documented.
- **Horizon (5):** Error codes are part of the versioned contract; errors include a machine-applicable fix where possible; consistency is tested.
- **Evidence:** error schema, error tests. **Probes:** `agent.structured_errors`. **Refs:** MCP, ISO25010.

#### INT-5 Idempotency and stable identifiers

**Question.** Can calls be retried safely, and are results, pages and records addressed by stable identifiers?

**Why.** Agents retry after timeouts and crashes. Stable ids enable caching, citation and deduplication across agents.

- **Fails (0-1):** Retries duplicate effects; identifiers change between runs.
- **Meets (3):** Safe retries for read operations and idempotency keys for writes; stable ids; cursor-based paging.
- **Horizon (5):** Content-addressed results that are shareable across machines, with identical ids for identical observations.
- **Evidence:** id scheme, retry semantics. **Probes:** `epi.evidence`, `dur.checkpoint`. **Refs:** MCP.

#### INT-6 Human usability and accessibility

**Question.** Does the quickstart work as written, are CLIs ergonomic, and do UIs meet WCAG 2.2 AA and support internationalisation?

**Why.** The European Accessibility Act applies from 2025; accessible software serves more people and is easier to automate.

- **Fails (0-1):** The quickstart fails; a UI is inaccessible to keyboard or screen-reader users.
- **Meets (3):** The quickstart is tested; help output is complete; UIs follow WCAG 2.2 AA with semantic markup; text can be translated.
- **Horizon (5):** Accessibility is tested automatically in CI; documentation and UI are localised; agent and human interfaces stay equivalent.
- **Evidence:** quickstart test, a11y checks, locales. **Probes:** `ui.a11y`, `ui.i18n`, `meta.translations`. **Refs:** WCAG, EU-EAA, ISO25010.

#### INT-7 Open formats and exit

**Question.** Can users export their data and results in open formats and leave without loss?

**Why.** The EU Data Act and procurement policies favour portability. Lock-in is a long-term liability for users.

- **Fails (0-1):** Proprietary formats only; no export.
- **Meets (3):** Export and import in documented open formats (JSON, JSONL, SQLite, SPDX/CycloneDX and so on).
- **Horizon (5):** Formats are specified and versioned, and third-party tools can read them.
- **Evidence:** export commands, format specs. **Probes:** `agent.json_output`, `dur.storage`. **Refs:** EU-DATA.

### EPI: Epistemic integrity

*What the product asserts is traceable, calibrated and honest about what it does not know.* ISO/IEC 25010: functional suitability.

#### EPI-1 Evidence and provenance of outputs (core)

**Question.** Does each result record what it was derived from (input digests, tool and version, parameters) so that it can be reproduced?

**Why.** Agent outputs flow into decisions. Without provenance they cannot be audited, cached or trusted.

- **Fails (0-1):** Bare conclusions with no traceable source.
- **Meets (3):** Results carry input identity, tool version and parameters.
- **Horizon (5):** Results are content-addressed, linked to their sources, and signed for exchange between parties.
- **Evidence:** result records. **Probes:** `epi.evidence`. **Refs:** ISO25059, SBOM.

#### EPI-2 Calibrated uncertainty and abstention

**Question.** Are confidence levels attached to claims and checked against outcomes, and does the product abstain when evidence is weak?

**Why.** Overconfident output is the main failure of AI-assisted analysis (OWASP LLM09 misinformation).

- **Fails (0-1):** Everything is stated with equal certainty.
- **Meets (3):** Claims carry a confidence class or probability; weak claims are flagged or withheld.
- **Horizon (5):** Calibration is measured on adjudicated outcomes (per-class precision with intervals, ECE), and abstention thresholds are fitted to a target error.
- **Evidence:** confidence fields, calibration reports. **Probes:** `epi.uncertainty`. **Refs:** ISO25059, NIST-AIRMF, OWASP-LLM.

#### EPI-3 Absence is not a negative

**Question.** When nothing is found, does the product say 'not found within this coverage' rather than 'does not exist'?

**Why.** Absence of evidence read as evidence of absence is the most common silent error in analysis tools.

- **Fails (0-1):** Empty results are reported as negatives.
- **Meets (3):** Missing results are labelled unknown, with the coverage that was examined.
- **Horizon (5):** Every negative claim carries its search boundary, and complete-versus-partial coverage is machine-readable.
- **Evidence:** limitations fields, coverage fields. **Probes:** `epi.coverage`. **Refs:** ISO25059.

#### EPI-4 Coverage accounting

**Question.** Does the product (or its report) separate what was examined, what was skipped, and what was never addressed?

**Why.** An investigation that does not know its blind spots reports false completeness.

- **Fails (0-1):** No notion of scope or coverage.
- **Meets (3):** Reports state scope, what was examined and what was skipped.
- **Horizon (5):** Declared questions or targets are reconciled with recorded outcomes automatically, and unaccounted items are surfaced.
- **Evidence:** coverage reports. **Probes:** `epi.coverage`. **Refs:** ISO25059.

#### EPI-5 Claims hygiene (red line)

**Question.** Do the README and docs claim only what measurements support, with dates and sources?

**Why.** Inflated claims mislead people and agents that select tools from descriptions.

- **Fails (0-1):** Claims contradicted by measurement, or superlatives without evidence.
- **Meets (3):** Numeric claims link to their measurements and dates; limitations sit next to the claims.
- **Horizon (5):** Claims are generated from benchmark results and cannot drift from them.
- **Evidence:** claims vs harness mapping. **Probes:** `claims.count`, `claims.harness`. **Refs:** ISO25010.

### MNT: Maintainability and architecture

*The code can be understood, changed and extended safely by people and agents.* ISO/IEC 25010: maintainability, flexibility.

#### MNT-1 Modularity and enforced boundaries

**Question.** Are layers and module boundaries explicit and checked automatically?

**Why.** Agents change code quickly. Enforced boundaries keep fast change from eroding the architecture.

- **Fails (0-1):** Everything imports everything; no stated architecture.
- **Meets (3):** The architecture is documented and boundaries are respected.
- **Horizon (5):** Boundary rules run in CI (architecture tests, dependency rules) and violations block merges.
- **Evidence:** architecture docs, boundary checks. **Probes:** `static.arch_guards`. **Refs:** ISO5055, ISO25010.

#### MNT-2 Size, complexity and duplication hygiene

**Question.** Are file and function sizes reasonable, duplication low, and dead or unreachable shipped code absent?

**Why.** Duplication and dead code multiply maintenance and attack surface, and they confuse agents reading the code.

- **Fails (0-1):** Large duplicated subtrees; shipped code nobody can reach.
- **Meets (3):** Duplication and dead-code checks exist; outliers are justified.
- **Horizon (5):** Size, duplication and reachability budgets are enforced per release.
- **Evidence:** duplication report, dead-code report, size outliers. **Probes:** `size.duplicates`, `size.largest`, `static.dupe_tools`, `static.deadcode_tools`. **Refs:** ISO5055.

#### MNT-3 Static analysis and type safety

**Question.** Are linting, formatting and type checking configured strictly and enforced in CI?

**Why.** Static checks are the cheapest defect filter and give agents fast feedback.

- **Fails (0-1):** No linters or type checks.
- **Meets (3):** Linters, a formatter and type checking are configured and run in CI.
- **Horizon (5):** Strict mode everywhere, with no unexplained suppressions, and checks run before every commit.
- **Evidence:** lint/type configs, CI jobs. **Probes:** `static.lint`, `static.format`, `static.types`. **Refs:** ISO5055.

#### MNT-4 Documentation for maintainers and agents

**Question.** Are architecture, decisions, contribution rules and agent instructions (AGENTS.md) written down and current?

**Why.** Coding agents are now routine contributors. Their instructions are part of the codebase.

- **Fails (0-1):** No contributor or architecture documentation.
- **Meets (3):** CONTRIBUTING, an architecture overview and agent instructions exist.
- **Horizon (5):** Decision records are kept; docs are checked for drift in CI; agent instructions are tested by running agents on tasks.
- **Evidence:** CONTRIBUTING, AGENTS.md, ADRs. **Probes:** `meta.contributing`, `meta.agents_md`, `meta.docs`. **Refs:** AGENTS-MD.

#### MNT-5 Debt is visible

**Question.** Are known shortcuts and debts recorded with the condition that triggers their repayment?

**Why.** Untracked debt surfaces later as outages.

- **Fails (0-1):** Debt is hidden in prose ('for now', 'temporary') or not recorded at all.
- **Meets (3):** Debt markers or an issue list with owners and triggers.
- **Horizon (5):** A debt ledger is generated from code markers and reviewed every release.
- **Evidence:** debt markers, ledger. **Probes:** `static.debt_markers`. **Refs:** ISO5055.

### EVO: Evolution, compatibility and release

*Users can upgrade predictably, on the platforms they run, for a declared period.* ISO/IEC 25010: compatibility, flexibility.

#### EVO-1 Versioning honesty

**Question.** Do version numbers mean what they say (breaking changes as majors, or a clearly documented policy), with migration guides?

**Why.** Agents and pipelines pin versions on semantic assumptions. Breaking changes in minor releases break them silently.

- **Fails (0-1):** Breaking changes without a version signal or notes.
- **Meets (3):** SemVer, or an explicit policy, plus breaking-change notes and migration guides.
- **Horizon (5):** The public contract is diffed automatically between releases, and breaking changes are detected and labelled by tooling.
- **Evidence:** CHANGELOG, version policy, migration guides. **Probes:** `meta.changelog`, `evo.semver`. **Refs:** SEMVER.

#### EVO-2 Release integrity and sustainable cadence

**Question.** Are releases qualified (tests, install rehearsal) and documented, at a cadence users can absorb?

**Why.** Release churn is a cost for every downstream user.

- **Fails (0-1):** Ad hoc releases with no notes or qualification.
- **Meets (3):** Automated releases with changelog and qualification steps.
- **Horizon (5):** Release channels (stable/LTS/next), staged rollouts and rollback paths.
- **Evidence:** release workflow, changelog cadence. **Probes:** `ci.release_automation`, `meta.changelog`. **Refs:** NIST-SSDF.

#### EVO-3 Platform and runtime compatibility

**Question.** Are the supported operating systems, architectures and runtime versions stated and tested?

**Why.** Agents run on heterogeneous hosts, including ARM, containers and edge devices.

- **Fails (0-1):** Untested platforms are claimed, or platforms are not stated.
- **Meets (3):** A support matrix is stated, and CI covers the main platforms.
- **Horizon (5):** The full declared matrix is tested, including containers and ARM, with graceful messages on unsupported hosts.
- **Evidence:** support matrix, CI matrix. **Probes:** `ci.os_matrix`, `evo.platforms`. **Refs:** ISO25010.

#### EVO-4 Support commitments (applies if `distributed`)

**Question.** Is a support period or end-of-life policy declared?

**Why.** The EU CRA requires manufacturers to declare and honour a support period for security updates.

- **Fails (0-1):** No statement of support.
- **Meets (3):** Supported versions and the support period are stated.
- **Horizon (5):** LTS lines with security-fix guarantees for the declared period, and end-of-life dates published in advance.

## 7. Opportunity criteria

Scored separately from quality. 0 means no opportunity found; 5 means a large, well-evidenced opportunity. A high-quality repository can still hold large opportunities, and a low-quality one can hold extractable gems.

- **OPP-1 Extractable foundations.** Is there a self-contained, high-value component that would be more useful as its own package or service? Signals: High in-degree hub with few outward dependencies; clean interface; value independent of the host product.
- **OPP-2 Consolidation.** Is the same capability implemented more than once, in this repository or across the reviewed set? Signals: Identical or near-identical files; same concept led by several repos; parallel implementations in several languages.
- **OPP-3 Composition multipliers.** Does pairing this capability with one from another repository produce more than the sum (shared ids, shared formats)? Signals: Complementary capabilities in the dissection graph; matching data shapes; shared identifiers.
- **OPP-4 Substitution and deletion dividends.** Could code, dependencies or surface be removed or replaced with something simpler that already exists? Signals: Reimplemented standard-library features; unreachable shipped code; unused tools; heavy dependencies for small tasks.
- **OPP-5 Re-platforming.** Would moving a component to another execution model fix structural limits (in-memory to durable, whole-object to streaming, cloud to on-device, heuristic to trained model)? Signals: Size cliffs; crash data loss; latency floors; repeated heuristics that a small calibrated model could replace.
- **OPP-6 Interface re-cut and standardization.** Would a smaller, composable interface or a published format let more people and agents use the capability? Signals: Large catalogs; duplicated payloads; internal formats other projects need; evidence records; coverage documents.
- **OPP-7 Horizon shifts.** Which 2030-35 shifts (agents as primary users, post-quantum cryptography, regulation, on-device inference, energy pricing, data sovereignty) turn a latent capability into a requirement? Signals: Capability that maps onto a dated obligation or standard; edge-deployable models; offline operation.

| RL-2 | SEC-6 | level 0 | Live secrets committed, or secrets exposed in outputs or logs. |

## 9. Scoring and grades

- **Criterion.** Each applicable criterion gets a level 0-5, U or NA, a confidence (observed, derived, inferred) and at least one evidence reference. Core criteria weigh 2, others 1.
- **Dimension.** D = sum(w_c * c_conf * s_c) / sum(w_c * c_conf) over applicable criteria with a known level. U and NA are excluded from the mean.
- **Evidence coverage.** E = known / applicable criteria, per dimension and overall.
- **Quality index.** QI = 20 * sum(W_d * D_d) / sum(W_d), with profile weights W_d. Range 0-100.
- **Horizon index.** HRI = 100 * mean over applicable known criteria of h(s), where h(5) = 1, h(4) = 0.5 and h(s<4) = 0. It shows how much of the 2030-35 bar is already met.
- **Grades.** A >= 80, B >= 65, C >= 50, D >= 35, E >= 0 (Quality Index).
- **Gate.** Any red line caps the grade at D.
- **Gate.** Evidence coverage below 60 percent marks the grade provisional (suffix "?") and caps it at C.
- **Gate.** A dimension with weight >= 2.5 in the profile and score below 2 is listed as a blocking weakness.
- **Opportunity priority.** Priority = Value (1-5) x Reach (1-5) x Confidence (0.5 inferred, 0.8 derived, 1.0 observed) x Horizon fit (1.0-1.5) / Effort (1-5).

## 12. Re-engineering actions

| Action | When |
| --- | --- |
| keep | High value and quality; no structural issues. |
| harden | Sound design with missing gates (tests, provenance, limits, errors). |
| refactor | Right behaviour, wrong structure (duplication, boundaries, size). |
| extract | Value >= 4 and portability >= 4, and the component is held back by its host (size, churn, coupling). |
| consolidate | Two or more implementations of the same capability; keep the best and retire the others. |
| re-platform | A structural limit (in-memory state, whole-object I/O, execution model) that patches cannot fix. |
| re-cut-interface | The capability is good but the interface is too large, too costly or inconsistent. |
| rewrite | Core component whose defects are structural, and whose contract can be kept stable during the rewrite. |
| replace | An existing component of equal or better quality does the same job (the necessity ladder says reuse). |
| retire | Unreachable, unused, or its cost (context, maintenance, risk) exceeds its value. |

Pick the least disruptive action that fixes the root cause. Record the evidence, the expected gain and how the gain will be measured.

## 13. Reviewer integrity

- Cite evidence for every score; prefer observed over inferred.
- Score what is shipped and maintained, not intentions or roadmaps.
- U is honest; do not guess a level to avoid it.
- No style taste and no 'consider' findings. Each finding states a case, an impact and a fix.
- Disclose conflicts of interest. Reviews of one's own work need an adversarial second reviewer.
- Compare against the profile and the anchors, not against other repositories.
- Record time spent and what was not examined.
