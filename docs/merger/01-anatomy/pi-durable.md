## 1. What it really is

pi-durable is an embeddable TypeScript library, not a CLI or a service. It runs LLM agent conversations as durable state machines on one storage owned by one process [seen, `durable:README.md:5`, `durable:README.md:783`]. All state goes through a single in-process "mutation line" of atomic commits. That state is transcript entries, tasks, submissions and JSON documents. Nothing is shown before its commit is stored (`durable:docs/spec.md:63-79`) [seen]. A model turn is a built-in task, `pi.generation`. Each tool call is its own task, `pi.tool`. The tool task commits its intent before the effect runs. After a restart it reruns only tools declared replay-safe. Every other interrupted call gets an "interrupted" result (`durable:src/harness/tool.ts:175-196`) [seen]. Around this core it ships:

- four coding tools copied from pi-coding-agent;
- a Node execution environment;
- a QuickJS "code mode" that replays deterministically;
- compaction;
- subagent and child-task ownership;
- live views and telemetry.

It does not authenticate to model providers itself. The host passes in a pi-ai `Models` object, and every credential question belongs to pi-ai (`durable:src/harness/types.ts:217`) [seen]. The best description is a crash-safe *agent kernel for a single process*, not a workflow engine [inferred]. It has no worker pool, no lease and no multi-host story. Its durability is strong for one owner and undefined for two.

### 3.2 What the storage layer itself promises

- **SQLite (Node).** WAL with `synchronous=NORMAL`: commits survive a process crash, but the newest can be lost on power or host failure [seen, `durable:README.md:762`; `chord:src/sqlite/node.ts:237-238`]. Busy timeout 5 s [seen, `chord:src/sqlite/node.ts:16`].
- **JSONL.** Survives an ordinary process crash, with torn-tail handling per spec. Without `fsync: true` (default false) there is no promise across power loss [seen, `durable:src/storage/jsonl/storage.ts:257`; `durable:docs/spec.md:5600-5602`].
- **Memory.** No durability [seen, `durable:README.md:761`].
- **Storage errors.** A storage error is fatal to the Harness. It closes itself and nothing is retried. Commits are atomic, so reopening is consistent [seen, `durable:README.md:816`].

### 3.3 Missing lease and concurrency behaviour

- **No owner lease, by design** [seen]. `durable:README.md:783` says "One process owns a storage at a time; there is no cross-process locking." Nothing in `Harness.open` checks for another owner [seen, `durable:src/harness/harness.ts:523-545`].
- **What SQLite still gives** [seen]. Each commit is `BEGIN IMMEDIATE` (`chord:src/sqlite/node.ts:144`), so two processes cannot interleave *inside* one commit, and the file stays well-formed.
- **What breaks with two owners** [inferred from code; no two-process test exists]:
  1. **Both resume all pending work.** Each open flips `running` to `pending` and dispatches (`durable:src/harness/scheduler.ts:375-410`). Replay-safe tools, generations (model calls) and child tasks run twice.
  2. **Duplicate IDs.** `mintId()` hands out IDs from a counter read once at open (`durable:src/storage/sqlite/storage.ts:176`, `:212-216`). A collision on a conversation, entry or document ID throws inside the commit (`:679-681`), which fails the Harness. A collision between two *task* or *submission* records of the same type passes the check (`:682-684`). It then hits `INSERT … ON CONFLICT(id) DO UPDATE` (`:821-823`, `:838-839`), so **one process can silently overwrite the other's task or submission record**.
  3. **requestId dedupe races.** It reads storage outside the SQL transaction (`durable:src/session/transaction.ts:279-281`), and the index is not UNIQUE (`durable:src/storage/sqlite/migrations.ts:63`).
  4. **Stale caches.** Each process's document trackers and live-task index never see the other's commits (`durable:docs/spec.md:1679-1696`).
- **Cloudflare Durable Objects.** The platform's single-instance rule supplies the missing exclusion [inferred]. The README's alarm protocol covers eviction, not a second owner [seen, `durable:README.md:166-207`].
- **Tests.** The tests themselves open a second Harness on a storage whose first Harness is still alive in memory (`durable:test/harness-tasks-recovery.test.ts:275-280`) [seen]. They depend on the missing exclusion rather than test it [inferred].

## 4. Environmental assumptions and blind spots

**Assumptions** [seen unless marked]:

1. **One process per storage, and one shared clock** for sleep deadlines (`durable:README.md:162`, `:783`).
2. **Node >= 22.19** for `node:sqlite` (`durable:package.json:143-145`). Bun is claimed but its testing is unconfirmed (EVO-3 note).
3. **POSIX-style process groups** for tree kill (`durable:src/env/node.ts:287-307`). A writable `tmpdir` for spill files (`durable:src/env/node.ts:1209`). Spill clean-up is unknown.
4. **The host supplies** models and credentials, the registry, and `env()`. The host must reinstall the same extensions after a restart, or tasks stay blocked (`durable:README.md:466-470`).
5. **Trust boundary = the user's account.** Prompt injection is out of scope (`pi:SECURITY.md:6-22`, `:56`). AGT-1 = 1 confirmed.
6. **API instability** is accepted: "The API changes without notice" (`durable:README.md:3`), and lockstep 1.x versions carry breaking changes (EVO-1 2, unconfirmed beyond `durable:CHANGELOG.md:9`).

**Blind spots:**

- No lease or fencing (§3.3).
- No built-in approval flow or pause (AGT-3 2, unconfirmed).
- No per-run token, money, call or depth budget (`durable:README.md:329`; AGT-6 2).
- Model requests are re-sent after a crash and this is not surfaced as a distinct report [inferred].
- No real process-kill or two-process test (organ 16).
- No provenance or taint on context entries for injection policy (G2, unconfirmed).
- No deletion of transcripts (PRV-2).
- Built-in tools are not confined to cwd, inherit secrets and have no timeout (organ 11).
- The coding agent, pi's main product, does not run on pi-durable: only `pi:packages/env/package.json:49` depends on it [seen]. So production mileage is unknown [unknown].

## 5. Contribution to a merged product

### 5.1 What pi-durable should contribute

1. **Intent-before-effect tool task with dual replay policy** (organ 6). It is small, readable and directly answers "did this side effect happen?" (`durable:src/harness/tool.ts:173-196`) [seen]. Lift with notice. Add a depth cap, a default approval gate and a budget.
2. **The phase/checkpoint task model, the effect-sandwich rule, and the restart-count parking guard** (organs 4, 5). Take these as a pattern, whatever store the merged product uses [inferred].
3. **requestId-idempotent submissions and the steer/follow-up inbox** (organ 8). Lift the semantics and add a UNIQUE constraint.
4. **The immutable transcript of typed entries**, with provider, model and usage per answer (organ 9; `durable:README.md:749-755`). It could serve as the agent-side half of an evidence ledger (inferred; whether it joins rea's ledger is for layer 3).
5. **Deterministic, journaled code-mode replay** (organ 13). Restartable, reproducible analysis scripts would be a real differentiator for an artifact-analysis product [inferred].
6. **Storage and environment conformance kits** (organ 16). Extended with kill-at-step-k and two-owner cases, one suite could certify every durable store in the merger, including an absurd-backed one (the review's O11; I agree) [inferred].
7. **Content-free telemetry schema** and the "views derive from commits, nothing shown before durable" rule (organs 1, 15).

### 5.2 What it should not contribute

1. **pi-ai's subscription OAuth paths** (organ 14). The Anthropic path presents as Claude Code (`claude-cli` user agent, `x-app: cli`, a Claude Code client id and scope, tool-name remapping). That conflicts with the charter's "never present as an official client" guardrail [seen; conclusion inferred]. The Codex/ChatGPT path is also unknown with respect to sanctioning. Subscription use in a merged product must come from a donor's delegated sign-in through the provider's own CLI, SDK or ACP, not from pi-ai.
2. **The built-in coding tools as they are** (organ 11). They are copies of pi-coding-agent (495/500 and 141/174 lines identical) [seen], and their defaults are permissive.
3. **JSONL and Memory storage** as production backends (organ 3).
4. **The Chord-coupled Session and document kernel** (organ 1) and the 2,507-line scheduler (organ 5) as code. Both are deep, experimental, and tied to chord's tracker model [inferred]. Lifting them would import pi's lockstep release churn (EVO-1).
5. **Its storage ownership model as the multi-process story.** It has none (§3.3).

### 5.3 Overlap with a Postgres engine like absurd (honest note)

- **What absurd has** [seen]. Multi-worker leased claims: `claim_task` takes a `claim_timeout`, default 30 s (`absurd:sql/absurd.sql:915-947`). Lease extension: `extend_claim` (`absurd:sql/absurd.sql:1555`). Per-step checkpoint state: `set_task_checkpoint_state` (`absurd:sql/absurd.sql:1468`). Events: `await_event`/`emit_event` (`absurd:sql/absurd.sql:1700`, `:1887`). A UNIQUE idempotency key on partitioned queues (`absurd:sql/absurd.sql:213-219`). Steps are recorded and replayed after failure (`absurd:README.md:27-31`).
- **Same layer.** pi-durable's task model, sleep, retries, child tasks and restart handling (organs 4, 5) solve the same problem for one process. The two engines sit at the *same layer*, and a merged product should not keep both as general workflow engines [inferred].
- **What absurd lacks** [inferred]. Agent semantics: transcripts, model-turn phases, partial-as-aborted, tool replay policy, compaction, inbox modes, subagent ownership, code-mode journal. These are pi-durable's real value, and absurd has none of them (no agent concepts seen in `absurd:sql/absurd.sql` function names).
- **Absurd as a pi-durable backend does not work by itself** [inferred]. pi-durable assumes one mutation line, in-memory ID minting and in-memory caches (§3.3). A Postgres `Storage` adapter would still need **one owner per Session**. The realistic join is to run each pi-durable Session as one absurd-claimed task, or to take an absurd-style lease per Session at `Harness.open`, and to mint IDs inside the transaction. The other route is to rebuild organs 6–9 as step functions on absurd. Both are design changes, not lifts.
- **Cost of the alternative** [inferred]. Absurd makes Postgres a hard dependency, which pi-durable avoids today (local SQLite, Durable Objects). Choosing absurd as the core loses the zero-service local mode. Choosing pi-durable as the core loses multi-worker failover. That trade is an **owner decision** for layer 4.
- **Null option** [inferred]. Composing them as they are works only by giving each its own store and accepting two durability models side by side.
